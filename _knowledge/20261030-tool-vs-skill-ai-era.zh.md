# 工具与技能：AI 时代两种执行方式的本质区别

![封面图：一只毛茸茸的橙色卡通小麒麟龙坐在书桌前，就着台灯光线在笔记本电脑旁的笔记本上写写画画，桌上放着一杯咖啡](/assets/resources/20261030-tool-vs-skill-ai-era/cover-zh.jpg)

进入 AI 时代，我们越来越依赖 AI 替我们做事：跑脚本、查资料、写代码、做部署。但"AI 替你做事"其实分成了两个层次，很多人把它们混为一谈——一个是**工具（tool）**，一个是**技能（skill）**。分清这两者，是设计任何 AI 自动化的第一道分水岭。

> 核心判断：工具按清单执行、异常即止；技能在调用工具脚本之上叠加模型推理兜底，并把新问题的解法沉淀回自身、越用越聪明。两者的区别不是"长短"，而是"是否带推理层"。

## 为什么这个概念重要 — 误区的代价

误解这个区别的代价是实实在在的：把需要随机应变的任务交给工具，它会在第一个清单外异常面前卡死；把本可以脚本化确定执行的任务全推给模型推理，token 成本又会失控。**分清两者的边界，就是分清"哪些事交给确定性，哪些事交给智能"。**

本文只谈概念层面的区别与取舍，不展开任何具体产品的实现细节。

## 心智模型 — 包含关系图

```text
                 任务请求
        ┌───────────┴───────────┐
        ▼                       ▼
  ┌───────────┐          ┌──────────────┐
  │   Tool    │          │    Skill     │
  │ 按固定清单 │          │ 模型推理在先，│
  │ 一步步执行 │          │ 再编排工具执行│
  │ 清单外异常 │          │ 清单外异常    │
  │ → 无力处理 │          │ → 推理自救    │
  └───────────┘          └──────┬───────┘
                                │ 内部仍调用
                                ▼
                         ┌──────────────┐
                         │  工具脚本     │
                         │ 确定步骤、省 token │
                         └──────────────┘
```

- **工具是执行单元**：输入在清单内，严格按清单逐步执行；一旦出现清单没覆盖的异常，它没有第二条路可走。
- **技能是编排单元**：先由 AI 模型做判断——这一步该怎么做、出了意外怎么调整——然后才去调用工具脚本真正干活。
- **技能内部依然尽量用脚本**：脚本的 token 成本远低于让模型一步步推理，确定的事不该浪费智能。异常兜底才靠模型推理完成——可以调用模型已有知识，也可以现场去网上抓技术文档查证，而不是原地报错。

## 运作机制 — 四层拆解

### 第一层：工具 — 按清单执行

工具的行为是预先写好的步骤序列。优点是确定、便宜、快；缺点是这份"便宜"的前提，是世界完全按预期运行。

### 第二层：技能 — 推理在先，执行在后

技能接到任务后，先由 AI 模型理解目标、拆解步骤，再调用内部工具脚本去执行。脚本负责确定的苦活，模型负责不确定的判断。

### 第三层：异常兜底 — 推理登场

这一层是工具与技能的分水岭。工具遇到异常就停；技能遇到异常，把上下文交给模型推理：模型可能凭已有知识直接解决，也可能去联网抓取技术文档，找到办法后调整方案继续执行。

### 第四层：自我演进 — 把解法沉淀回自身

当技能靠推理解决了一个之前没碰到过的问题，它会把这次的经验固化为自身的一部分——更新自己的流程、规则，或补一段工具脚本——让同类问题下次不再需要临时推理，而是直接命中。**工具永远学不会新东西，因为清单写定就不动；技能会越用越聪明，正是因为每解决一次意外，它都在重写自己。**

```text
# 工具：按清单跑，异常即止
for step in CHECKLIST:
    run(step)                  # 失败就停，没有兜底

# 技能：调用工具 + 推理兜底 + 自我演进
for step in plan:
    if not run_tool(step):
        clue = model.reason(context)      # 凭知识或联网查文档
        plan = model.replan(plan, clue)   # 调整方案，继续执行
        skill.learn(step, clue)           # 沉淀解法，下次直接命中
```

注意第 3 行与第 6、7 行的对比：工具在第 3 行失败即终止；技能在第 6 行把失败交给模型推理兜底，在第 7 行又把解法沉淀回自身——前者换来执行流的延续，后者换来下一次的"不用再想"。

## 常见误解 — 四个澄清

- **"技能就是更长的工具清单。"** 不是。清单再长也是静态的，技能多了推理层——它能在运行时改主意，这正是处理清单外异常的能力来源。
- **"有了技能，工具就没用了。"** 恰恰相反。确定、重复的步骤交给脚本跑，token 成本最低、结果最稳；技能的价值在异常与判断，不在抢工具的活。
- **"技能什么都能自己搞定。"** 也不对。技能真正动手时依然要调用工具脚本——模型负责"想"，脚本负责"做"，缺了执行层，推理只是纸上谈兵。
- **"技能每次遇到异常都得从零开始想。"** 不是。解法会沉淀回自身；下次同类问题直接命中，不必再临时推理。

## 何时应用 — 分工清单

- 设计 AI 自动化流程时，先逐个问："这一步的结果是确定的吗？"确定 → 做成工具脚本；不确定 → 留给技能的推理层。
- 发现任务总在某个"清单外异常"上卡住，这就是把工具升级为技能的明确信号。
- 在意 token 成本时，把可脚本化的部分尽量下沉，让模型只在异常与决策时出手。
- 选型时问两个问题：异常会不会出现？解决异常需不需要查资料？只要有一个答案是"会 / 需要"，就选技能。

---

## 总结

1. 工具按固定清单执行、异常即止；技能在调用工具脚本之上叠加模型推理兜底异常，并把新问题的解法沉淀回自身——技能包含工具，而且会自我演进。
2. 对日常最重要的启示：确定的事交给脚本，不确定的事才交给推理，别让智能浪费在清单能解决的地方。
3. 下次设计自动化时，先问自己："这一步会遇到清单外的异常吗？"需要自救，就把它交给技能。

如果你在搭建 AI 自动化时踩过"工具卡死"或"token 失控"的坑，欢迎在评论区聊聊。
