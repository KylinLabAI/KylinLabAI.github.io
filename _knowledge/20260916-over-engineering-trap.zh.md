# 过度工程化陷阱——换更强的模型解决不了，清晰的需求才能

![封面图：过度工程化陷阱——换更强的模型解决不了，清晰的需求才能](/assets/resources/20260916-over-engineering-trap/cover-zh.jpg)

你可能会直觉地以为：全模型（DeepSeek 4.0 Pro、GLM-5.2 等）能力最强，修简单 Bug 应该最干净。但真实翻车恰恰相反——**全模型在修一个简单 Bug 时，反而更容易甩出一个过度复杂的重构方案**。

更关键的是：**换更强的模型解决不了这个问题**——能力越强，不给明确需求时做过头的概率越高。

## 为什么值得看

这个缺陷很反直觉，也很有迷惑性：大重构方案看起来"专业、全面、有诚意"，但它让简单问题变复杂、改动范围失控、回归风险陡增。而且很多人会因此走向另一个误区——觉得"换个更强的模型就能修好"，结果反而更糟。这一篇讲透全模型为什么倾向过度工程化，以及为什么清晰的需求和 scope 约束才是真正的解药。

## 你将学到三点

1. **换更强的模型解决不了过度工程化**——能力越强、上下文越大，不给明确需求时做过头的概率反而越高。解药不是升模型，是写清需求。
2. **清晰的需求 + 显式的 scope 约束才是核心手段**——在 Prompt 里限定改动范围、要求「优先最小改动并解释为何不需大改」，比换任何模型都有效。
3. **看到大重构方案先反问「真的需要吗」**——把"最小化"作为默认，把"扩大范围"当作需额外证明的例外。

## 背景与选型思路

修 Bug 时的方案选择，本质是在**改动范围**与**改动正确性**之间权衡。理想情况下，简单 Bug 就该用最小改动修好，但不同模型对"该改多大"的默认判断不同。

**关键认知：换更强的模型不是解药。** 很多人遇到过度工程化的第一反应是"是不是该换个更强的模型"——恰恰相反，全模型能力越强、上下文窗口越大，它越倾向于主动发现问题并顺手修复，做过头的概率反而更高。解药从来不是升模型，而是写清需求、限死 scope。

| 方案 | 优点 | 缺点 | 适合 |
|---|---|---|---|
| 最小改动 | 范围小、回归风险低、易 review | 可能不够"优雅" | 简单 Bug、线上修复 |
| 顺带重构 | 更彻底、顺手优化结构 | 范围失控、回归风险高 | 已有重构计划时 |

问题出在：**全模型把"修 Bug"默认理解成"重构代码库"，而不是"改这一处"**。它的目标是产出一个"完整、优雅"的解决方案，而非一个"最小、安全"的修复——于是简单问题被过度工程化。

对比 Flash 版：Flash 能力弱一些，反而没那么容易做过头，因为它「想不到那么多」。全模型恰恰因为能力强、上下文大，才更倾向于「主动发现更多问题并一并修复」——**能力越强，不给详细需求时做过头的概率越高**。这意味着：遇到过度工程化，升级模型不仅无效，反而可能让情况更糟。真正有效的是在 Prompt 里写清需求、限死改动范围。

## 方案总览

防御方案的核心是：**在任务定义里显式限定改动范围，并让"最小化"成为默认、可被质疑的例外**——这不是靠换模型能解决的，而是靠写清需求。

- **明确限定 scope**：修复简单 Bug 时，在 Prompt 里写清只改哪一处、不扩范围。
- **要求最小改动**：加约束「优先选择最小改动方案，解释为什么不需要更大范围修改」。
- **默认最小、例外需证明**：把"小改动"设为默认，任何扩范围的方案都需给出理由。
- **对大重构先反问**：看到大重构方案，先问"真的需要吗"，再决定是否采纳。
- **保持 diff 可 review**：修复改动保持小而清晰，让人工一眼能核对该改了什么。
- **区分修复与重构**：修 Bug 就是修 Bug，重构留给专门的计划，别在一次修复里混着来。

**设计规则（不变式）：**

- 简单 Bug 修复**默认最小改动**；任何扩大范围的方案必须给出"为什么小改动不够"的证明。
- 修复类任务**显式限定 scope**，防止全模型顺手把重构带进来。
- **不要试图用更强的模型来解决过度工程化**——这是需求问题，不是能力问题。

## 一个真实的翻车案例

一个简单的 URL-to-image 映射顺序错误，GLM-5.2（全模型）最初选择了**过度复杂的重写方案**，在被明确指出后才承认 "I overcomplicated this"，回归到最小改动。

![GLM-5.2 过度工程化后被纠正回最小改动](/assets/resources/20260916-over-engineering-trap/wrong_approach_overcomplicated_GLM-5.2.png)

## 效果与收益

- **之前**：一个 URL-to-image 映射顺序错误，模型先给出过度复杂的重写方案，被人指出后才知道改复杂了，绕了一段弯路才回到最小改动。
- **之后**：Prompt 里立了"优先最小改动并解释为何不需大改"的约束，简单 Bug 一次就修到最小范围。

省下的是**返工与 review 成本**：改动范围小、diff 清晰、回归风险低。

> **关键提醒：** 全模型（DeepSeek 4.0 Pro / GLM-5.2）的能力越强，**不写明详细需求就越等于允许它自由发挥**。模型的默认策略是「发现问题就修」，而不是「只修你要求的」。不要指望换一个更强的模型来解决过度工程化——更强的模型只会把问题放大。真正有效的是在 Prompt 里写清需求、限死改动范围：一条简单的约束（如「只改这一处，不做其他改动」）就能把行为拉回正轨。

## 总结

1. **换更强的模型解决不了过度工程化**——能力越强、上下文越大，需求越模糊时做过头的概率反而越高。升模型是错误方向。
2. **清晰的需求 + 显式的 scope 约束才是解药**——在 Prompt 里限定改动范围、要求「优先最小改动并解释为何不需大改」，比换任何模型都有效。
3. 全模型（DeepSeek 4.0 Pro / GLM-5.2 等）的默认策略是「发现问题就修」，而不是「只修你要求的」——一条简单的约束（如「只改这一处，不做其他改动」）就能把行为拉回正轨。
4. 看到大重构先反问"真的需要吗"——最小改动是默认，扩大范围需额外证明。

下次全模型甩来一个大重构方案时，别急着叫好，也别想着"换个更强的模型会不会更好"——先问一句"最小改动真的不够吗"，然后把需求写清楚。
