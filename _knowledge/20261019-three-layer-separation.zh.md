# 知识、调度、档案三层分离：AI 交付系统的仓库分层法则

![三座积木仓库塔分别标着知识、调度、档案，塔间由符号链接锁链环环相扣](/assets/resources/20261019-three-layer-separation/cover-zh.png)

> 系列：Idea-to-Production · 概念篇。同系列：《人不在环内：一个 AI 自主交付组织的概念契约》、《九个角色如何分掉一家公司：一张不会漂移的 Agent 组织图》；机制层深潜可阅《无人值守调度的三件机件：认领锁、中心推送、幂等键》。

一个跑通的 AI 交付系统，最难维护的往往不是 Agent 的提示词，而是"什么该放在哪"。改一个技能清单要不要重新部署调度服务？加一个角色要不要动平台代码？本文用**变化速度**和**所有权**两个维度回答这类问题：把整套系统切成知识、调度、档案三层，每层一个仓库，并给出守住边界的四条纪律与违反它的代价。

> 一句话结论：**按功能分层是错的，按变化速度分层才是对的**——每天都变的内容，和几个月才动一次的平台，绝不该住在同一份部署里。

## 为什么值得看

多数 Agent 框架在演示阶段浑然一体：一个仓库装下 Agent 定义、调度服务、任务数据和文档产物，跑通演示只要几分钟。可一旦要长期演进就处处掣肘：改一个技能清单要重新部署调度服务，加一个角色要动平台代码，工作实例本地"顺手改"的提示词永远不会被任何人看见。

这不是某个框架的 bug，是**混层**的必然结果——变化速度完全不同的东西，被塞进了同一份部署里。

本文给出一个可以直接抄走的分层判据，并用我们系统的三仓库结构作对照。不涵盖每个仓库的内部实现（那是机理层诸篇的事），也不涵盖具体部署方式。

## 你将学到三点

1. **按变化速度分层，而不是按功能分层。** 每天都变的"怎么做"，和几个月才变一次的"谁来调度"，必须物理隔离。
2. **资源用符号链接绑定，绝不用复制。** 复制即漂移——这是多实例系统里唯一能保证"改了就生效"的方式。
3. **跨仓库只走配置，不硬编码路径。** 层的边界靠约定维持，不靠"碰巧在同一台机器上"。

## 一个典型的失败模式

假设把一切放在一个仓库里：Agent 定义、调度服务、任务数据、文档产物混住。半年后你会遇到：

- 想优化某个角色的技能清单，提交必须过一次调度服务的回归测试，否则不敢合并；
- 调度器升级版本，所有角色定义被连带锁定在旧运行时上；
- 两台工作机各自持有资源副本，同一个角色在不同实例上行为不一致，排查一下午，发现只是某台机器忘了同步。

三条症状指向同一个病因：**内容的变化速度和基础设施的变化速度被绑死在同一份部署里。**

## 判据：两个维度切三层

| 维度一：变化速度 | 维度二：谁有权改 |
|---|---|
| 知识层（各角色怎么工作）——几乎每天变 | 由框架的"作者"演化，跨项目共享 |
| 档案层（产出了什么）——每个项目都在增长 | 由交付过程自动书写，人来归档 |
| 调度层（谁、何时、干哪条）——数月才动一次 | 由平台实现，追求稳定，尽量不改 |

把两个维度叠起来，系统自然裂成三层，每层一个仓库：

| 仓库 | 公司类比 | Essence |
|---|---|---|
| **知识层** | 员工手册 | 纯内容，客户端无关（不依赖任何特定 AI CLI）：角色定义、技能、工作流、领域知识 |
| **调度层** | 办公室与工单系统 | 可执行平台：控制中心（项目、任务、认领锁、作业运行器、审计）+ 工作实例客户端（拉任务 → 拼提示词 → 启动 AI CLI） |
| **档案层** | 档案室与橱窗 | 文档库：开发期草稿、已发布应用文档、运行报告、任务模板 |

三层各自回答一个问题：**知识层说"下一步做什么"，调度层说"哪个实例、什么时候、且只有一个工人去做"，档案层存"做出了什么"并喂给下游。** 缺一层，另外两层立刻失去意义。

判据的用法很朴素：拿到任何一个新文件，先问两句话——它多久变一次？谁有权改它？答案会把它放进唯一的那层。按变化速度分家，演进速度互不拖累。

## 分完之后，靠四条纪律守住边界

分层容易，守层难。我们把边界写成了不容协商的不变式：

1. **绝不把技能、工作流、Agent 定义放进调度仓库或档案仓库。** 内容永远进知识层。
2. **绝不在运行逻辑里硬编码机器相关路径或跨仓库绝对路径。** 一切通过配置解析——这也是知识层能保持客户端无关的原因。
3. **工作实例通过符号链接绑定知识层资源，绝不复制。** 改动即时生效、全实例共享，副本漂移的可能性被物理消除。
4. **一次提交绝不横跨两个仓库。** 顶层工作目录不是仓库——三层各有自己的 git 历史，这本身就是"层之间存在"的每日提醒。

再加一条元纪律：**同一条原则只允许存在于一份文档里。** 复述即分叉；需要引用时，链接到真源。

## 概念落到界面上是什么样

在调度层的桌面客户端里，创建一个工作实例只需要**选角色**；该角色在知识层绑定的全部资源——Agent、技能、工作流、知识库——自动以符号链接出现在实例的工作空间里。一份"员工手册"是如何被"办公室"领取上岗的，一眼可见：

![创建实例时选中角色，该角色在知识层绑定的 Agent、技能、工作流、知识库随即以符号链接出现在实例工作空间](/assets/resources/20261019-three-layer-separation/instance-resources-bindings.png)

界面上这一步，正是四条纪律中第 2、3 条的物理兑现：资源由配置解析、由符号链接绑定，所以"选角色"之后无需任何手工同步，也不存在第二份可以漂移的副本。

## 总结

1. **分层判据可以直接迁移到任何 Agent 系统**：先问"这个文件多久变一次、谁有权改"，再决定它住在哪一层——按变化速度分家，演进速度互不拖累。
2. **符号链接是"单一真源"的物理实现**，多实例共享资源时，复制方案在架构上就是错的，不是"暂时能用"。
3. **现在就检查你自己的系统**：改一次提示词，需要重新部署调度服务吗？如果答案是"是"，你的系统正在混层，本文的失败模式清单就是你的体检表。
